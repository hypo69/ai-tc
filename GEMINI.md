## 📋 Master Overview



Этот файл является **главным индексом инструкций** для проекта. Он связывает все проектные документы, архитектурные принципы и инженерные стандарты.



> [!IMPORTANT]

> **Языковой стандарт**: Вся документация, docstrings, комментарии к коду, сообщения коммитов и описания тестов **ДОЛЖНЫ** быть написаны строго на **русском языке**. (Имена переменных, функций и классов в коде остаются на английском языке в соответствии с PEP 8).

> [!IMPORTANT]

> **Фиксация времени изменения в шапке файла**: При любом изменении кода в файле в шапку файла **ОБЯЗАТЕЛЬНО** записывается/обновляется время изменения файла (`Updated: YYYY-MM-DD HH:MM:SS`).

> [!IMPORTANT]

> **Вывод сообщений в консоль**: Когда поступает запрос вывести сообщение — вывод **ОБЯЗАТЕЛЬНО** выполняется через `logger.console()` исключительно для вывода в консоль без записи в файл.

> [!IMPORTANT] Нет обратной совместимости! Чем меньше кода – тем лучше.

## 💡 Концепция проекта (AI Windows Admin)



**Назначение:** Интерактивный «макет» (ai-windows-admin) для тестирования, бенчмаркинга и бесшовной маршрутизации между различными провайдерами и средами выполнения ИИ (Windows AI APIs, Microsoft Foundry Local, Windows ML / ONNX Runtime, Ollama, Google Gemini, OpenAI-совместимые API и HuggingFace).







## 📚 Стандарты разработки



Вся разработка **ДОЛЖНА** следовать инструкциям в `.ai/instructions/`:



### 1. **Инженерные стандарты**

📄 [`.ai/instructions/standards/ENGINEERING.md`](.ai/instructions/standards/ENGINEERING.md)



Ключевые требования:

- Архитектурные принципы: Явное внедрение зависимостей (DI), Fail-Fast, DRY, Single Responsibility

- Стандарты языка: Python 3.12+ (код на Python по PEP 8, docstrings и комментарии строго на русском языке)

- Обязательное обновление даты и времени модификации (`Updated: YYYY-MM-DD HH:MM:SS`) в шапке каждого изменяемого файла

- Запрет недокументированных возвратов `None`

- Лимит длины файлов: максимум 500 строк функционального кода (до +20% при необходимости). Исключение: «неразрывные» файлы длинных определений (SQL, схемы таблиц, декларативные шаблоны/установки). При этом управление каждой таблицей строго выносится в отдельный файл

- Стандартизированное логирование через `logger`

- Строгое разделение конфигурации (`config.json`) и секретов (`.env`)



### 1.1. **Фундаментальный стандарт системной инженерии (Beyond Vibe Coding)**

📄 [`.ai/instructions/standards/SYSTEM_ENGINEERING.md`](.ai/instructions/standards/SYSTEM_ENGINEERING.md)



Ключевые требования:

- **Неблокирующий I/O и защита Event Loop:** Запрет `time.sleep` и синхронного I/O в корутинах, обязательное закрытие дескрипторов (`with` / `finally`), ограничение кэшей через TTL/LRU.

- **Данные, сложность и транзакции:** Сложность $O(1)$ через `set`/`dict` вместо $O(N^2)$, батчинг/JOIN против N+1, категорический запрет `float` для денег (`Decimal` / минимальные целые единицы), строгий UTC ISO 8601, защита от Lost Update (атомарный SQL, оптимистичные/пессимистичные блокировки), режим WAL в SQLite.

- **Сети и распределенные системы:** Обязательные таймауты (`connect`/`read`) на каждый сетевой вызов, `Exponential Backoff + Jitter`, `Circuit Breaker`, `Idempotency-Key` для мутирующих запросов, паттерн `Transactional Outbox` против Dual-Write.

- **Безопасность и Observability:** Защита от BOLA/IDOR и SQL/Command инъекций, строгий CORS без wildcard с credentials, структурированные JSON-логи с `trace_id` (W3C `traceparent`), метрики RED с перцентилями `p50`/`p95`/`p99` и Property-Based тестирование.





### 2. **Повторное использование кода и аудит существующего кода**

📄 [`.ai/instructions/standards/REUSE.md`](.ai/instructions/standards/REUSE.md)



Ключевые требования:

- **Обязательный предварительный аудит:** Перед разработкой новых функций, компонентов UI или системных инструментов выполните поиск по кодовой базе (`grep_search`, `find_by_name`). Обязательно проверяйте реализованные подсистемы в `/apps` и особенно системный стек в [`/apps/windows`](apps/windows) (`SystemCollector`, `SystemSnapshot`, `apps/windows/core`, `apps/windows/hardware`).

- **Запрет изолированных инструментов-дубликатов:** Запрещено строить отдельные функции/скрипты для операций, под которые в `/apps` уже создана модульная архитектура. Все новые параметры и операции интегрируются строго в существующие классы, коллекторы и модели данных.

- **Единообразие кода:** Повторно используйте или расширяйте существующие реализации (выпадающие списки, модальные окна, паттерны API); не создавайте дублирующие реализации.

## 📧 Почтовая инфраструктура



Все почтовые ящики (IMAP/SMTP) должны управляться централизованно через файл `src/secrets/mailboxes.json`.



**Правила:**

- **Single Source of Truth**: Все агенты и скрипты обязаны считывать конфигурацию из `src/secrets/mailboxes.json`. Жесткое кодирование параметров запрещено.

- **Алиасы**: Используйте поле `aliases` в `mailboxes.json` для выбора ящика через естественный язык.

- **Унифицированный агент**: Для работы с почтой используйте унифицированный почтовый диспетчер, который обеспечивает прозрачный доступ ко всем настроенным ящикам.



> [!WARNING]

> Никогда не коммитьте `src/secrets/` в репозиторий.

## ✅ Чек-лист перед коммитом



Перед каждым коммитом проверьте:



- [ ] Выполнен поиск готовых решений в кодовой базе и аудит подсистем `/apps` (особенно `/apps/windows`) (REUSE_RULES.md)

- [ ] Заголовок файла соответствует стандарту (`FILE_HEADERS.md`): при любом изменении кода в шапку файла записано актуальное время изменения (`Updated: YYYY-MM-DD HH:MM:SS`)

- [ ] Все docstrings, комментарии, логи и документация написаны на **русском языке**

- [ ] Все публичные функции и классы содержат docstrings в формате `hypo69 docblock`

- [ ] Логирование выполняется через `logger` (без прямых вызовов `print`), а вывод сообщений в консоль без записи в файл — через `logger.console()`

- [ ] Длина файлов не превышает 500 (+20%) строк функционального кода; для неразрывных определений (схемы таблиц) каждая таблица содержится в отдельном файле

- [ ] Все секреты и ключи вынесены в `.env`

- [ ] Новые приложения в `/apps` зарегистрированы в общем сервере (`src/app/__init__.py`) и меню администратора (`index.html`, `main.js`) (CODE_RULES.md § 4.5)

- [ ] **Темизация без хардкода:** Проверено полное отсутствие хардкода цветов и стилей (HEX, RGB, `style="color:...", style="background:..."`). Всё оформление выполнено строго через механизм тем (`var(--...)`) и классы дизайн-системы (`ui-badge`, `ui-card` и др.)

- [ ] При изменениях фронтенда (HTML/CSS/JS/JSON) обновлена версия ассетов `?v=YYYYMMDD_vN` и обеспечен cache-busting для предотвращения показа кешированных данных

- [ ] Коммит представляет собой **логически завершённое, протестированное состояние** рабочего кода

- [ ] Тесты проходят: `pytest tests/ --cov`

- [ ] **Вкладки и Карта сайта:** Все каталоги вкладок названы строго по шаблону `tab_<tab_id>`. Карта сайта `tab_sitemap` актуализирована через `generate_sitemap_data.py`.

- [ ] Новые директории содержат `README.md` на русском языке

> [!NOTE] Все файлы и директории, имена которых начинаются с тильды (`~`) автоматически исключаются из обработки проекта.

## 🤖 Правила неинтерактивного запуска команд

- При выполнении команд через `run_command` ВСЕГДА автоматически добавляй флаги автоподтверждения и молчаливого режима (`-y`, `--yes`, `--quiet`, `-Force`, `-Confirm:$false`).

- Если утилита требует интерактивного ввода через stdin, автоматически оборачивай вызов в пайплайн (например, `echo y | py ...` или `cmd /c "echo y | ..."`).

- Не останавливай выполнение длительных процессов для запроса подтверждений у пользователя.
